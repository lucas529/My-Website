Context

This is the project that made real-time systems actually click for me. The whole class was really one long build: write a real-time operating system from scratch in C, then trust it to drive a real car. There was no pre-made scheduler and no shortcuts, so a bug was never just a red underline in an editor. It was a car that wouldn't stop.

Approach

The heart of the whole thing is the scheduler, so that is where most of my time went. I made it preemptive and priority based, with Rate Monotonic admission control, which is a fancy way of saying it only accepts a new task if it can actually promise to run everything on time. Sharing resources safely was the harder part. I used priority-ceiling mutexes so a low-priority task can't quietly hold up a high-priority one, and getting that right took a lot of failed test runs and a few long nights with a waveform viewer.

Build

It came together in stages, one lab at a time. First a custom PCB to wire the STM32 up to the car's motor, then the kernel itself, one piece at a time: a bootloader, device drivers, timers and interrupts, and finally the scheduler and mutexes. Once the kernel could stand on its own, I connected it to the car. The PID controller closes the loop on encoder feedback, with live speed and PID terms on an onboard LCD and a small Python tool graphing target versus actual speed in real time. I built it with a partner, and we passed the course's test suite one stubborn case at a time.

Result

In the end, it drove. The car held its target speed on top of a kernel I had written from nothing, and it passed the full test suite. The grade was nice, but the real takeaway was simpler: you can't hand-wave timing when a wheel is actually spinning. That is the lesson that made embedded systems stick for me.

lab 1 · bootloader
Wrote the bootloader that loads and starts our own code on the board. My note in the README at the time was just: "it was a bit strange."
lab 2 · drivers & MMIO
Built the device drivers and memory-mapped I/O, the layer that actually lets your code read and write the hardware.
lab 3 · timers, interrupts, and system calls
Added the OS primitives underneath everything: timers to keep time, interrupts to react to the world, and system calls to cross safely between user code and the kernel.
lab 4 · the real-time kernel
The big one. A preemptive, priority-based kernel with Rate Monotonic admission control and priority-ceiling mutexes, all validated against the course's test suite.
lab 5 · motor control
Everything comes together: the finished kernel driving the car with PID control, live telemetry on an LCD, and a Python plot of target versus actual speed.
